## 2026-09-20 · 小球交叠的真实根因

- 坑：我最初以为「圆形交叠」只是个视觉密度问题，加个列表模式绕开就行。实际读代码才发现根因是算法问题：固定直径 220rpx + 「随机撒点 + 每颗最多试 200 次的拒绝采样」+ 重力(0.05) 远大于回锚柔力(0.0035)。商品一多，采样必然全部失败退化成互相压着的随机位置，同时泡泡还会往底部堆挤——**不改排布算法，小球模式切回去照样交叠**。
- 解决：把排布抽成纯函数 `utils/bubbleLayout.js`（自适应半径 220→104rpx + 错位网格，几何保证任意两颗中心距 ≥ 2r），并写 `tests/bubbleLayout.test.js`（5 种容器 × 11 种数量 × 20 遍随机抖动 = 2316 条断言）防回归。测试当场抓出「极小容器 + 翻页多」仍会交叠的边界，补上「按容量截断 + 提示切列表模式」。物理也调了参：重力降到 0.012、回锚力升到 0.012、碰撞位置修正迭代 2 次。
- 下次指令补充：涉及几何/物理排布的需求，请给一个「数量上限」（比如「首页最多同时展示多少个」），或者明确允许加自动化回归测试——否则「看起来不挤」只能靠肉眼，改一次参数就要重新肉眼看一遍。

## 2026-09-20 · 逐色替换的三个坑（配色统一）

- 坑一：脚本把 `wx.showModal({ confirmColor: '#f43f5e' })` 也换成了 `var(--error)`。原生接口的颜色参数走原生层，**不认 CSS 变量**，传进去会被当非法值忽略，按钮悄悄退化成默认色——WXSS 里看不出任何异常，只有真机点开弹窗才发现。
- 坑二：深琥珀 `#b45309`、`#7a4a00` 这类「浅底上的状态文字」被逐色映射成了价格色/警告色，而 `--warning` 压 `--warning-soft` 只有 1.9 的对比度，小字直接糊成一片。逐色替换只保证「色值对」，保证不了「文字在它的底上读得清」。
- 坑三：`var(--want, #00a8a0)` 这种「带兜底值」的写法，替换把兜底值也换成了另一个令牌（`var(--want, var(--type-idle-text))`），语义错位；而别名改名脚本只匹配 `var(--want)`，漏掉了它。
- 解决：① 加 `utils/nativeColors.js` 集中收原生 API 色值；② 补 `--warning-dark` / `--success-dark` 两个「浅底深档」令牌（原站本来就有这个层次，是我压平了）；③ 写 `tools/theme-contrast.py` 按 WCAG 对比度复核，把 29 条低对比降到 17 条（剩下的是品牌渐变上的白字小角标，属设计语言）；④ 清掉所有 `var(--x, fallback)` 写法。
- 下次指令补充：配色类指令请明确「低对比度的小角标（20rpx 白字压绿渐变）是否也要一并修」。这条不写清，执行者只能拿 WCAG 硬抠，很容易把既有设计语言改重；我这次是保守处理（只修真读不出来的），需要确认这是你要的口径。

## 2026-10-09 · 白屏排障：WXSS 注释后多一个分号

- 坑：开发者工具表现为「编译成功，但模拟器一片空白」，而「调试控制台」和「问题」两个面板**都不显示任何错误**。真凶在 `pages/admin/admin.wxss:850`：
  `color: var(--warning);   /* 状态/提示语义，不是价格 */;` —— 声明已用 `;` 结束，注释后面又多了个 `;`。
  **标准 CSS 会忽略这个多余分号，WXSS 的严格解析器则直接抛 `unexpected token ;`**，属编译级致命错误，整个样式表挂掉、页面白屏。全库共 **14 处**，分布在 13 个文件里，注释文字完全一致——是那次「配色统一」批量替换脚本留下的伤（`24e0123`）。
  我最初按「是不是我这次改坏的」方向查了三轮（WXML 标签配对、JSON 合法性、页面真实加载），全部通过，因为**根因根本不在我改的文件里**——`admin.wxss`、`privacy.wxss`、`home.wxss` 我一行都没碰过。
- 解决：写脚本按 `;  /*注释*/;` 精确匹配（含跨行与连续分号变体）一次修完 14 处；把检查固化成 `tools/checkWxss.js`；并新增 `tools/checkWxml.js`（标签闭合 + mustache 配对）、`tools/checkPageLoad.js`（真实 require 每个页面）补上静态自查的盲区。顺带确认：`app.json` 里我为排查临时去掉的 `batch_invite` 行已恢复。
- 下次指令补充：① **报错信息比代码更值钱**——「无法编译」这类问题，请第一时间把开发者工具里**报错的完整原文**（文件路径 + 行号 + 错误类型）发我，而不是只说「编译不了」。这次是我先问、你后给，给出了之后我 2 分钟就定位了；在此之前我做了三轮全库静态排查全是白工。② 批量脚本改动的文件（如逐色替换、批量重命名）建议**单独一次提交、并当次就编译验证**——这次的 14 处伤是脚本留下的，但因为没人当场编译，一路潜伏到了下一次改动才暴露，很容易被误判成「新改动搞坏的」。
